# Wave 8 CLS + LCP before/after evidence (provisional)

Generated by the W8-4 harness (`tools/perf/run.mjs`). Read the caveats before quoting numbers: the
compressed "after" run was interrupted by a mid-run rebuild, so its JSON is marked
`summary.distChangedDuringRun: true` / `target.consistency: changed-during-run`; only cells measured
before that rebuild are used below. The final post-integration re-run replaces this file.

## Method

- Profile: slow-4G (1.6 Mbps down / 750 kbps up / 150 ms RTT) + CPU ×4, Playwright Chromium 1.65
  from `rebuild/node_modules`, parity mocks (Supabase empty JSON, 1×1 PNG image stub, video/audio
  aborted), fresh browser context per run, 1 warm-up + 3 measured runs, median.
- "Compressed" = `node tools/perf/run.mjs --serve-dist rebuild/dist` (local static server serving the
  build with gzip, i.e. how a static host delivers it). "Preview" = `--url http://127.0.0.1:4175`
  (the Lead's `vite preview`, which serves the emitted bytes **uncompressed**).
- Budgets (QUALITY_BAR): CLS ≤ 0.05, LCP ≤ 2000 ms (LCP target is the mobile profile).

## Residual CLS risk — uncompressed preview is timing-dependent

The same fixed build, served by `vite preview` **without response compression**, still measures the
old values (3 runs each, all valid):

| Route      | mobile CLS | desktop CLS |
| ---------- | ---------: | ----------: |
| `/`        |     1.0293 |      0.6389 |
| `/gallery` |     1.0000 |      0.6389 |
| `/film`    |     1.0000 |      0.6389 |

Recorded shift source is again the `footer`. Reason: without compression the route chunk arrives
after the shell's 1.5 s fallback timer, so the footer mounts before the page has content height and
is pushed down when content arrives. Production Brotli/gzip hides this, but a genuinely slow network
can hit the same sequence — a time-based fallback races the network. Recommended hardening: reserve
height in the shell fallback (e.g. `min-h-[100svh]` placeholder) or mount the footer only after the
main region has height, instead of a fixed 1.5 s timer.

## LCP — measured, NOT fixed (pending W8-1 prerender)

Compressed server, valid cells of the post-fix build (median):

| Route      | mobile LCP | desktop LCP |
| ---------- | ---------: | ----------: |
| `/`        |    3344 ms |     3632 ms |
| `/gallery` |    3348 ms |     3460 ms |
| `/film`    |    2196 ms |        n/a¹ |

All exceed the 2000 ms budget. Caveats that must travel with these numbers:

1. Mocked image requests return a 1×1 PNG stub, so the LCP element is below-fold **text**
   (`p.mt-2.max-w-xl`, `a.shrink-0.px-3`, …) instead of a real hero image — contentful LCP will move
   once a build with real data/media env is measured.
2. This is a client-rendered SPA: first paint waits for the initial JS chunk (159.92 KiB gzip after
   the route-splitting fix) to download **and parse/execute** under ×4 CPU throttle.
   Pre-rendered HTML + hydration (W8-1) is the structural lever; until that build lands, LCP is
   **measured but not fixed/verified**.

Preview mode (uncompressed) shows the same structural shape with inflated values: LCP 5.7–6.0 s
across `/`, `/gallery`, `/film` (median, 3 runs) — these numbers describe the preview server's
missing compression more than the app.
