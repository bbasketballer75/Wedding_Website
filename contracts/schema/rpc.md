# RPC Inventory — every public function, its contract, and its callers

Generated by backend-eng (Wave 0) from a clean local Supabase reset of the frozen migrations
(`rebuild/greenfield` @ `legacy-freeze-2026-11-08`). Authoritative source: `pg_proc` +
`pg_policies`/`pg_proc.proacl` in the reset database, not `supabase/schema.sql` (stale).

Reproduce:

```bash
docker exec -i supabase_db_theporadas-workbench psql -U postgres -d postgres -X -A -F '|' \
  -c "select p.proname, pg_get_function_arguments(p.oid), pg_get_function_result(p.oid),
             p.prosecdef, p.provolatile, coalesce(p.proacl::text,'')
      from pg_proc p join pg_namespace n on n.oid = p.pronamespace
      where n.nspname='public' and p.prokind='f' order by p.proname;"
```

Result: **21 functions in `public`** — 10 called by `src/**`, 1 trigger function, 10
defined-but-unused-by-src (rate-limit helpers called from other functions, superseded versions,
service-role admin helpers, one read RPC only used by scripts/tests). All 21 are `SECURITY DEFINER`
except the trigger function; all are `VOLATILE` except `is_admin()`, which is `STABLE`. Owner is
`postgres` (migrations run as the migration role).

Grant matrix comes from `proacl` (`{=X/...}` means PUBLIC EXECUTE):
`anon`/`authenticated`/`service_role` can execute most app RPCs; the three admin/service-role
functions (`promote_to_admin`, `demote_from_admin`, `update_auth_user_metadata`) have
`postgres,service_role` only; `is_admin()` and `get_recent_photo_comments_v1` etc. are narrower.
Where an anon grant is retained, the function body enforces `is_admin()` or input validation — see
§4 risk notes.

### 1.1 Behaviour notes for the rebuild (must-preserve semantics)

1. **`get_photo_like_statuses`** — pure read over `photo_likes` for an array of photo keys, plus a
   per-session `liked` flag. Empty array input is safe (returns zero rows). No auth required; the
   session id is a client-generated fingerprint.
2. **`get_photo_engagement_summary_v1`** — counts likes, visible comments and hidden comments per
   key in one round trip (gallery grid). `comments_count` counts only `is_hidden = false`;
   `hidden_comments_count` only `true`.
3. **`toggle_photo_like_v2`** — atomic like/unlike: validates non-empty `p_photo_key` and
   `p_session_id`, deletes the `(photo_key, session_id)` row when present, inserts otherwise
   (`on conflict do nothing`), then returns the authoritative `(likes_total, liked_now)`.
   The v2 column names are `result_*` (a v1 wrapper with `photo_key/likes_count/liked` still exists;
   src normalises v2 → the shape in `src/lib/supabase/photos.ts:95-104`). Concurrent toggles converge
   because the unique `(photo_key, session_id)` constraint is the arbiter.
4. **`create_photo_comment_v1`** — trims inputs, enforces author ≤ 60 chars, content 1–1000 chars,
   requires a session id, rate-limits to 5 comments per session per 10 minutes, inserts with
   `is_hidden = false`, returns the row. The table has a redundant CHECK
   (`char_length(btrim(content)) between 1 and 1000`).
5. **`get_recent_photo_comments_v1`** — admin listing joining `photo_comments` to `photos` by
   `p.id::text = pc.photo_key` (loose join; no FK). `limit` is clamped to ≥ 1. Raises
   `admin access required` when `not is_admin()`.
6. **`hide_photo_comment_v1`** — admin soft-hide/restore: sets `is_hidden`, `hidden_at`,
   `hidden_by_user_id = auth.uid()`, `hidden_reason`. Returns the updated tuple.
7. **`delete_photo_comment_v1`** — admin hard delete, returns `(deleted_id, photo_key)`.
8. **`save_album_organization_v2`** — the admin album organiser transaction: validates album is one of
   the four allowed names, rejects invalid target albums / photos no longer in the album, deletes
   requested photos (plus their likes/comments by `photo_key`), renumbers the selected album order,
   moves photos between albums with new `album_sort_order`, then renumbers remaining rows. Returns
   `(saved_album, current_album_count, moved_count, deleted_count)`. Uses `pg_temp` staging tables and
   raises on stale state. v1 (3 return cols) is superseded and unused by src.
9. **`delete_gallery_photos_v1`** — admin delete by ids and/or urls; deletes dependent likes/comments
   by `photo_key` (text) then the photos; returns deleted ids (keys) and urls. Empty target set
   returns zeros instead of erroring.
10. **`submit_guestbook_message_with_rate_limit`** — intended flow: read client IP from
    `request.headers` (`x-forwarded-for`/`x-real-ip`), call `check_rate_limit(ip,'guestbook_submit',
    p_max_requests, p_window_minutes)`, return a friendly `success=false` result when limited, bump the
    counter via `increment_rate_limit`, insert the message (storing `ip_address`), return
    `(success, message_id, error_message, rate_limit_remaining, rate_limit_reset_after)`.
    **The INSERT still names the dropped `type` column (and `p_type` arg), so the function raises
    `column "type" of relation "guestbook_messages" does not exist` before inserting — see §3.**

## 3. Known defect — the guestbook submit RPC is broken (documented, NOT fixed in Wave 0)

Proven on the clean local baseline:

```sql
select * from public.submit_guestbook_message_with_rate_limit(
  'Fixture Guest', 'fixture@example.com', 'Synthetic message', 'text', null, 3, 1);
-- ERROR:  column "type" of relation "guestbook_messages" does not exist
-- CONTEXT: PL/pgSQL function submit_guestbook_message_with_rate_limit(...) line 34 at SQL statement
```

Cause: migration `20260410001200_drop_guestbook_type_and_anniversary.sql` dropped
`guestbook_messages.type`; the hand-reconstructed migration #141
(`20260624000000_fix_guestbook_rpc_drop_type.sql`) repaired only the *read* RPC
(`get_guestbook_messages_with_comments`), not this write RPC. The function body still has:

```sql
INSERT INTO guestbook_messages (name, email, content, type, media_url, ip_address, reactions)
VALUES (p_name, p_email, p_content, p_type, p_media_url, v_ip_address, '{}'::jsonb)
```

Blast radius: `src/pages/guestbook/useGuestbookComposer.ts:96-133` calls this RPC first; on error it
falls back to a direct PostgREST insert into `guestbook_messages` (allowed by the public INSERT
policy), so the user-visible flow still works but **server-side rate limiting and the server-derived
IP attribution are bypassed**. The client-side limiter (3 submissions/minute, localStorage) remains.
`get_guestbook_messages_with_comments()` itself is healthy (returns the 5 baseline demo rows).

Decision (Lead, 2026-11-08, risk register R17): do **not** add a repair migration in Wave 0 — the
baseline must describe what the frozen repo ships, defects included, and changing the signature would
change shipped behavior during the rebuild. Fix is owned by Wave 3 / cutover:

```sql
-- NOT APPLIED — Wave 3 / cutover only
drop function if exists public.submit_guestbook_message_with_rate_limit(
  text, text, text, text, text, integer, integer);
create function public.submit_guestbook_message_with_rate_limit(
  p_name text, p_email text, p_content text,
  p_media_url text default null,
  p_max_requests integer default 3, p_window_minutes integer default 1)
returns table (success boolean, message_id uuid, error_message text,
               rate_limit_remaining integer, rate_limit_reset_after integer)
language plpgsql security definer set search_path = public
as $$ ... same body minus type/p_type ... $$;
revoke all on function ... from public, anon;
grant execute on function ... to anon, authenticated;
```

Cutover verification (read-only): compare `pg_get_functiondef('public.submit_guestbook_message_with_rate_limit'::regproc)`
against this baseline; if production already differs, reconcile before deciding the rebuild's shape.
`scripts/verify-migration-prod.mjs` is the existing read-only prod inspection helper (it checks the
admin-role functions; extend it to all public RPCs).

## 4. Function-grant / security notes

- `anon` retains EXECUTE on admin-gated RPCs (`save_album_organization_v1/v2`,
  `delete_gallery_photos_v1`, `hide_photo_comment_v1`, `delete_photo_comment_v1`,
  `get_recent_photo_comments_v1`). Each body starts with `if not public.is_admin() then raise
  exception 'admin access required'`, so anon calls fail safely, but the rebuild should revoke anon
  EXECUTE and grant only `authenticated` (with internal `is_admin()`), keeping `service_role` for
  maintenance.
- `toggle_photo_like_v2`, `create_photo_comment_v1`, `check_rate_limit`, `increment_rate_limit`,
  `get_photo_*` are intentionally public (anon) APIs.
- `promote_to_admin` / `demote_from_admin` / `update_auth_user_metadata` are `SECURITY DEFINER`
  writing `auth.users`; they are correctly revoked from public/anon/authenticated and must only ever
  run with the service-role key from trusted server tooling.
- `is_admin()` is `SECURITY DEFINER` + `STABLE`, reads only the JWT claim, and is the single role gate
  used by RLS and the admin RPCs after migration 20260623000100. Do not reintroduce
  `user_metadata.role` checks (the rebuild note: `user_metadata` is user-spoofable).
- All other public functions are `VOLATILE` with `search_path = public` where security-relevant;
  `check_rate_limit`/`increment_rate_limit`/`submit_guestbook_*` do **not** set `search_path`
  (SECURITY DEFINER without a pinned path is a hardening gap; rebuild should add it).
