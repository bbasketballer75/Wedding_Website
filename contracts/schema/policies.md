# RLS Policy Inventory — every policy per table and operation

Generated by backend-eng (Wave 0) from a clean local Supabase reset of the frozen migrations
(`rebuild/greenfield` @ `legacy-freeze-2026-11-08`). Source of truth is the local database, not
`supabase/schema.sql` (stale, 170 lines / 4 tables).

Reproduce:

```bash
npx supabase db reset --workdir tmp/supabase-sandbox   # sandbox recipe: see INVENTORY.md §1
docker exec -i supabase_db_theporadas-workbench psql -U postgres -d postgres -X -A -F '|' \
  -c "select schemaname, tablename, policyname, cmd, roles::text, qual, with_check
      from pg_policies where schemaname in ('public','storage')
      order by schemaname, tablename, cmd, policyname;"
```

Result on the clean reset: **18 public tables, 35 public policies, 8 storage-object policies,
43 policies in total**. RLS is enabled on 16/18 public tables; policy counts per table are in
[`INVENTORY.md`](./INVENTORY.md). Only `activity_log` and `photo_likes` have RLS **disabled**.

Auth model: admin is `auth.jwt() -> 'app_metadata' ->> 'role' = 'admin'` through
`public.is_admin()` (SECURITY DEFINER, `stable`, EXECUTE granted to `authenticated` only). Older
policies that still say `auth.role() = 'authenticated'` are *not* admin checks — any authenticated
user passes them. See §3 for the risk analysis.

Legend: `cmd` = SELECT / INSERT / UPDATE / DELETE / ALL (ALL covers every command); `roles` = table
roles the policy applies to (PostgreSQL adds these to the `TO` clause); `using` = row visible/filtered
expression; `with check` = rows allowed to be written.

## 3. Risk analysis of the baseline policy set

These are findings for the rebuild/cutover, not changes made in Wave 0 (no DB or policy was modified;
the rebuild owns the corrected policies).

### 3.1 `activity_log` has RLS disabled and zero policies (High)

The table is exposed through PostgREST in the `public` schema, and Supabase's default privileges grant
`anon`/`authenticated` ALL on public tables. Effect: anon can read the (public-intent) feed *and*
write/delete rows directly, bypassing the triggers. `/activity` only needs SELECT. Fix at rebuild:
`enable row level security` + a `for select using (true)` policy (and no write policies) — that alone
closes the write surface.

### 3.2 Public SELECT on emails (`guest_identities`, `guest_share_tokens`, `guest_uploads.via RPC`) (Medium)

`guest_identities` SELECT `using (true)` exposes `email` for every guest who ever claimed a photo;
`guest_share_tokens` SELECT `using (true)` exposes the full `(guest_email, token)` mapping, and the
token is the only secret protecting `/guest/:token` showcase pages. An anon client can enumerate
tokens, then read that guest's approved uploads + guestbook entries. The current client needs
token lookup by token value only, not table-wide read. Fix at rebuild: replace with a
SECURITY DEFINER `get_guest_contributions(p_token)` and drop public table SELECT; move the claim flow
to an RPC too. The rebuild must preserve the product behavior (share link works without an account)
without table-level enumeration.

### 3.3 `photo_likes` RLS disabled (Medium)

Direct anon INSERT/DELETE on `photo_likes` bypasses `toggle_photo_like_v2` (no per-session abuse
control beyond the unique `(photo_key, session_id)` constraint). Fix: enable RLS with no policies and
keep the SECURITY DEFINER RPC (the intended design).

### 3.4 `guest_uploads` "authenticated" policies are not admin-checked (Medium)

`Allow authenticated read all` / `Allow authenticated update` let *any* authenticated user read all
pending uploads (guest names + emails + media) and update any row (e.g. set `status='approved'`, or
change `guest_email`). The product only has owner/admin accounts (`app_metadata.role = 'admin'`), so
practical exposure depends on whether other auth users are ever created. High-risk for the rebuild:
use `is_admin()` for admin reads/updates.

### 3.5 `guestbook_messages` DELETE vs RLS (Medium, functional)

The admin moderation UI deletes guestbook messages directly (`src/pages/admin/GuestbookModeration.tsx`
lines 61/97) but no DELETE policy exists. Either the production database has an out-of-band policy
(schema drift — must be reconciled at cutover) or admin deletion is silently failing. The rebuild must
route deletion through a SECURITY DEFINER RPC (`delete_guestbook_message_v1`) with `is_admin()`, and
the fixture + e2e must cover it.

### 3.6 `moderation_audit_log` actor fields are client-supplied (Low-Medium)

The log is append-only by policy, but `actor_user_id`/`actor_email`/`actor_name` come from the client
(`recordModerationAudit()` in `src/lib/supabase/moderation.ts`) rather than from `auth.uid()`/`auth.jwt()`.
An authenticated admin could forge another actor. Better design: insert via RPC that derives the actor
from the JWT. Not exploitable by anon (INSERT requires authenticated), so severity is moderate.

### 3.7 Old-style role checks vs `is_admin()`

Policies written before 20260623000100 use `auth.role() = 'authenticated'`. The atomic migration
repointed the 7 admin-gated policies and 7 SECURITY DEFINER RPCs to `is_admin()`, but the
`guest_identities` / `photo_claims` / `guest_share_tokens` / `guest_uploads` / `guestbook_messages` /
editorial / audit-log policies still use the old check. That is consistent with those tables having
public read or append-only semantics, but the rebuild should decide per table (admin-only vs public)
rather than carry `auth.role()` forward.

### 3.8 Function grants

`pg_proc.proacl` shows many SECURITY DEFINER functions still grant EXECUTE to `anon` (e.g.
`save_album_organization_v1/v2`, `delete_gallery_photos_v1`, `toggle_photo_like*`,
`get_recent_photo_comments_v1`, `hide_photo_comment_v1`, `delete_photo_comment_v1`,
`create_photo_comment_v1`, `check_rate_limit`). Each of those has an internal `is_admin()` or
validation guard, so anon calls fail with `admin access required`/validation errors — but the
principle is wrong: revoke anon EXECUTE and grant the narrowest role. `promote_to_admin`,
`demote_from_admin`, `update_auth_user_metadata` are correctly service-role only. Full per-RPC grant
matrix: [`rpc.md`](./rpc.md).
